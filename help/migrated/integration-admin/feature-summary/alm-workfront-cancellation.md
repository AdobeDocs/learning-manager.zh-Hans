# ALM-Workfront取消/更新触发器

## 概述

Adobe Learning Manager (Learning Manager)现在可以根据Workfront中所做的更改取消并重新激活讲师引导和虚拟讲师引导(ILT/VILT)会话。 如果公司在Workfront中安排会话，并通过将Workfront迁移至Learning Manager的方式将其引入Learning Manager，则可以在迁移数据中将每个会话的状态设置为“活动”或“已取消”。 然后，Learning Manager会应用更改，就如同管理员在用户界面中取消会话一样。

通过迁移取消会话的行为与从Learning Manager用户界面取消会话相同。 一个刻意的区别是重新激活，如[重新激活已取消的会话](#reactivate-a-cancelled-session)中所述。

### 要求

会话的更新，如日期和时间、讲师、位置或链接及容量，均已通过迁移从Workfront流向Learning Manager。 取消没有。 在Workfront中取消会话后，无法了解Learning Manager相关内容，导致出现以下问题：

* 学习者继续注册了不再运行的会话，导致困惑和没有上课。
* 管理员必须在Learning Manager中手动重复取消操作。
* Workfront和Learning Manager失去同步，影响了Workfront作为日程安排的真实来源。

### 工作原理

1. 交付经理取消Workfront中的会话。
1. 迁移数据中的会话行包含新的会话状态列，该列设置为“已取消”。
1. 系统管理员通过API运行迁移。
1. Learning Manager会将匹配的会话标记为已取消，并发送与从用户界面取消会话时相同的通知。

>[!NOTE]
>
>此功能扩展了现有迁移过程，而不是添加第二个实时集成路径。

## 用例

在Workfront中启动的取消涉及以下角色。

### 涉及的角色

| 角色 | 描述 |
|---|---|
| 交付经理 | 在Workfront中安排和管理培训日历，包括取消会话。 交付经理不使用Learning Manager用户界面。 迁移是客户取消订阅后进入Learning Manager的唯一途径。 |
| 系统管理员 | 通过API运行迁移。 此角色负责操作Workfront到Learning Manager管道，且独立于交付经理和Learning Manager管理员。 |
| 管理员 | 在Learning Manager用户界面中管理课程和会话数据。 在被告知Workfront中的更改后，管理员不再需要手动取消会话。 |
| 作者 | 在Learning Manager用户界面中负责课程和会话内容。 |
| 讲师 | 已分配给会话。 讲师会看到正确的会话状态，并在他们所指示的会话被取消时收到通知。 |
| Prime 中的讲师 | 通过Learning Manager注册会话。 会话取消后，学习者会立即收到通知。 |

### 常见情景

| 情景 | 您执行的操作 | 结果 |
|---|---|---|
| Workfront中的会话被取消，例如，由于资源不可用或供应商出现问题。 | 在会话的迁移行中将会话状态设置为“已取消” ，然后运行迁移。 | Learning Manager中的会话已取消，且受影响的人员会收到通知。 |
| Workfront中活动会话更改的详细信息。 | 在迁移行中包含更改的值。 将会话状态设置为活动，或将其留空。 | 会话已更新。 Learning Manager会发送会话更新电子邮件。 |
| 已取消的会话将在Workfront中恢复。 | 在迁移行中将会话状态设置为“活动”，然后运行迁移。 | 会话变为活动状态，可以再次修改和取消。 |
| 系统会发送已取消会话的更新详细信息，但不将状态设置为“活动”。 | 用户无需执行任何操作。 | 会话保持取消状态，该行返回验证错误，并且未更改任何详细信息。 |
| 迁移行不包括会话状态。 | 将该列留空或将其忽略。 | Learning Manager中会话的当前状态保持不变。 |

## 主要功能

* **会话状态列。** 迁移架构包含一个可选会话状态字段，该字段支持“活动”和“已取消”。
* **通过迁移取消。** 当某行的状态为“已取消”时，Learning Manager中的匹配会话将会取消。 Learning Manager使用与迁移已用于创建和更新会话的相同匹配密钥。
* **Learning Manager中没有手动工作。** 管理员无需在用户界面中再次取消会话。
* **与用户界面中的取消行为相同。** 注册处理、面向学习者的可见性、报告、审核记录和通知与从用户界面取消订阅相匹配。
* **重新激活。** 通过在迁移数据中明确设置状态，可将已取消的会话重新设置为“活动”。
* **已取消会话的保护。** 迁移不会更改已取消会话的详细信息，除非该行明确将状态设置为“活动”。
* **向后兼容性。** 状态列是可选的，因此现有迁移文件可以继续工作，而不会发生更改。
* **完成通知。** 学习者、讲师、管理员、作者和经理会收到与从用户界面取消订阅相同的取消电子邮件。

## 会话状态

Learning Manager中的每个会话都处于以下两种状态之一。

| 状态 | 含义 |
|---|---|
| 活动 | 默认状态。 此课程为实时课程，学习者可以注册并参加。 |
| 已取消 | 会话已取消。 注册的学习者、管理员、作者和经理会收到通知，因为他们要从用户界面中取消订阅。 |

### 迁移的状态过渡规则

下表显示了处理迁移行时会发生的情况。 Learning Manager会使用迁移已用于创建和更新的匹配密钥来识别会话。

| Learning Manager的当前状态 | 迁移行中的会话状态 | 结果 |
|---|---|---|
| 会话不存在 | 活动或空白 | 会话被创建为活动状态。 |
| 活动 | 活动或空白 | 会话保持活动状态。 将应用行中更改的值。 |
| 活动 | 已取消 | 会话将被取消并发送通知。 |
| 已取消 | 已取消 | 该行将被跳过。 无法再次取消已取消的会话。 |
| 已取消 | 活动 | 此时会重新激活会话。 将应用行中更改的值。 |
| 已取消 | 空白 | 会话保持取消状态。 如果行更改了值，将返回验证错误，并且不会更改任何详细信息。 |

### 会话状态列的规则

* 每行上的列都是可选的。
* 当该列为空时，会话将更新为“活动”。
* 只有在该列明确显示为“活动”时，会话才会通过迁移再次变为活动状态。

在会话状态列中使用以下值之一：

* `state = Active`
* `state = Cancelled`

>[!NOTE]
>
>正在确认准确的列标题和接受的值。 使用迁移文档指定的名称。

## 已取消会话的更新

无法通过迁移更新已取消会话的详细信息。 如果取消的会话中的某行包含更改后的值，且未将状态设置为“活动”，则Learning Manager会返回验证错误、取消会话并且既不应用也不存储更改后的详细信息。 Learning Manager不会为尝试发送会话更新电子邮件。

### 使用迁移取消会话

如果已取消Workfront中的会话，并希望Learning Manager反映更改，请遵循以下过程进行操作。

**开始之前**

* 会话已存在于Learning Manager中，可通过Workfront到Learning Manager迁移进行导入。
* 您了解您的迁移用来识别会话的匹配密钥。

1. 在&#x200B;**Workfront**&#x200B;中，取消会话。
1. 在用于迁移的会话CSV文件中，找到该会话所在的行。 确保匹配的密钥与创建会话时使用的密钥相同。
1. 在会话状态列中，输入&#x200B;**已取消**。
1. 通过API运行迁移。
1. 在Learning Manager中，确认会话已取消。

Learning Manager会将会话标记为已取消，像处理从用户界面取消会话一样处理已注册的学习者，并发送取消通知。 无需在Learning Manager用户界面中执行任何操作。

>[!NOTE]
>
>如果会话已取消，Learning Manager会跳过该行。

### 更新活动会话

对于活动会话，现有迁移更新行为仍然可用。 将会话状态设置为“活动”或将其留空，并在行中包含更改的值。 您可以通过迁移管道继续更新详细信息，如日期和时间、讲师、位置或链接以及容量。

处于活动状态会保持现有的创建和更新行为。 “已取消”会通过会话CSV迁移调用用户界面提供的相同会话取消功能。

### 重新激活已取消的会话

只有在将状态明确设置为“活动”时，已取消的会话才会恢复为活动状态。 您可以通过迁移或在用户界面中编辑会话来重新激活会话。

1. 在会话CSV文件中，找到已取消会话的行。 确保匹配的密钥与创建会话时使用的密钥相同。
1. 在“会话状态”列中，输入“活动”。
1. （可选）更新行中要更改的任何其他值，如日期和时间、讲师、位置或链接或容量。
1. 通过API运行迁移。

会话变为活动状态，并可修改其详细信息。 通过迁移或通过用户界面重新激活的会话可以通过任一路径再次取消。

>[!IMPORTANT]
>
>如果发送已取消会话的更新会话详细信息而未将状态设置为“活动”，则会话将保持取消状态，该行将返回验证错误。

## 通知

在通过迁移取消会话时，Learning Manager会从用户界面发送每封请求取消的电子邮件。 不会缩小收件人的覆盖范围，并且内容使用相同的模板，因此收件人无法判断取消订阅是如何开始的。

以下是适用于此会话的收件人。

| 收件人 | 通知 |
|---|---|
| 学习者 | 已注册会话的学习者会被告知会话已取消。 |
| 讲师 | 分配给会话的讲师会收到取消通知。 |
| 经理 | 经理会收到取消通知。 |

### 已取消会话的电子邮件

已取消的会话不会生成已更新会话的电子邮件。 取消会话后，对日期和时间、讲师、位置或链接和容量的更改不会触发会话更新电子邮件。 只有取消和重新激活通知适用于已取消的会话。

## 注意事项和限制

* 由于该功能使用迁移，因此在迁移运行时，Learning Manager会收到在Workfront中作出的取消。 不支持基于Webhook的实时取消。
* 迁移无法更改已取消会话的详细信息。 要更改这些更改，请首先将状态设置为“活动”。
* 会话状态列是可选的。 省略它的行不会更改会话的状态。
* 该功能扩展了现有的迁移集成。 它不会添加第二个实时集成路径。
* 迁移计划或触发器取决于您的组织用来运行它的工具。 本指南不定义固定计划。
* 交付经理只能在Workfront中工作。 他们无需访问Learning Manager用户界面即可取消会话。

## 成功量度

| 衡量标准 | 目标 |
|---|---|
| 管理员或客户支持手动复制的取消 | 在发布后的一个完整发布周期内减少到0。 |
| Learning Manager中反映的Workfront取消请求 | 在一个迁移周期内处理了100%的取消事件。 |
| 用户界面和迁移取消之间的通知奇偶校验 | 针对已取消的会话，收件人覆盖范围（管理员、作者、经理和学习者）方面存在0个空白以及0封不必要的更新电子邮件。 |

## 故障排除

| 问题 | 预期或可能的原因 | 操作 |
|---|---|---|
| 在Workfront中取消会话后，该会话将保持活动状态。 | 迁移尚未处理取消，或者迁移行没有显示已取消状态。 | 验证迁移输入和处理结果。 |
| 已取消会话的详细信息不会更改。 | 会话保持取消状态时的预期行为。 | 通过将状态设置为活动来重新激活会话，然后应用更改。 |
| 对于已取消的会话，不会发送任何会话更新的电子邮件。 | 预期行为。 已取消的会话禁止发送普通更新电子邮件。 | 请使用取消订阅和重新激活生命周期，而不是仅含详细信息的更新。 |
| 跳过取消行。 | Learning Manager中的匹配会话已取消。 | 无需进一步取消。 如果会话必须恢复为活动状态，请先重新激活该会话。 |
| 收件人收到与用户界面取消相同的取消电子邮件。 | 预期行为。 旨在匹配用户界面的迁移取消。 | 无需执行任何操作。 |
| 当会话状态为空时，行为不明确。 | 在空白状态处理上，源要求存在冲突。 | 在依靠空白状态进行任何过渡之前，请确认释放行为。 |
